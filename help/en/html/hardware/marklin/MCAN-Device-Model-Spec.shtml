MCAN Device Model Specification Analysis and Improvement Proposals

Applies to Branch: refactor/mcan-library-and-bridge-2
Reference Issue: ralflang/JMRI#3 (Spec: Represent MCAN Bus Devices as JMRI entities)
Packages: jmri.jmrix.marklin.*

1. Overview & Evaluation Criteria

This document analyzes the MCAN (Marklin CAN) device model specification proposed in issue #3 and outlines concrete architectural improvements based on three primary criteria:

  1. Fit with the rest of the JMRI codebase (integration with Manager and NamedBean interfaces, system connection memo lifecycle, system naming, and thread safety).
  2. Similarity and consistency with other command buses in JMRI (specifically BiDiB, CBUS, and OpenLCB/NMRANet node lifecycle models, parameter abstractions, and UI monitoring tables).
  3. Promoting reusability of the protocol and message codec layer outside a fully bootstrapped JMRI environment (standalone bridges such as McanTcpBridge, microservices, CLI applications, or embedded gateways).

2. Evaluation & Recommended Improvements

2.1 Criteria 1: Fit with the Rest of the JMRI Codebase

A. Proper Manager and NamedBean Hierarchy Integration

  • Issue in Spec: Section 3.2 defines McanDevice as a plain POJO, deferring NamedBean / Manager integration to an optional "Step 6".
  • Improvement: McanDevice should implement or extend jmri.ProvidedSystemBean / jmri.implementation.AbstractNamedBean from the outset. Discovered nodes on hardware buses in JMRI are consistently managed via a standard Manager<McanDevice> (extending jmri.managers.AbstractManager<McanDevice>).
  • System Name Convention: Use standard system name prefix notation: M:dev:<toSystemIdFragment()>. For example:
    • Native MCAN device: M:dev:uid-00112233
    • CdB CAN-digital-bahn device: M:dev:cdb-22-03 (class 0x22, module 3)
  • System Connection Memo Lifecycle: The McanDeviceManager instance must be registered with and owned by MarklinSystemConnectionMemo (via memo.store(McanDeviceManager.class, deviceManager) and accessed via memo.get(McanDeviceManager.class)), allowing multi-system support without static singletons.

B. Threading Model and Event Dispatching

  • Issue in Spec: Uses CompletableFuture for asynchronous discovery and parameter operations without specifying thread handover rules.
  • Improvement: While CompletableFuture provides a clean async API for background transport operations, state changes (e.g. PropertyChangeEvent for device online/offline transitions, device creation, parameter updates) must strictly be dispatched on the Swing Event Dispatch Thread (EDT) or via jmri.util.ThreadingUtil.runOnGUI() to ensure thread safety across JMRI UI components.

2.2 Criteria 2: Consistency with Other Command Buses (BiDiB, CBUS, OpenLCB)

A. Node/Device State Machine Lifecycle

  • Bus Comparison:
    • CBUS (jmri.jmrix.can.cbus.node): Tracks node states, parameters (NVs), events, and initialization sequences explicitly via CbusNode.
    • BiDiB (jmri.jmrix.bidib): Uses BiDiBNode with explicit states (e.g. OFFLINE, DISCOVERED, INITIALIZING, UP).
    • OpenLCB (jmri.jmrix.openlcb): Uses MimicNodeStore and explicit state tracking.
  • Improvement for MCAN: Replace pure timestamp comparisons (lastSeen, lastPingReply) with an explicit McanDeviceState enum: 
    public enum McanDeviceState {
    DISCOVERED,    // Ping reply received, identity established
    INITIALIZING,  // Follow-up parameter reads in progress (e.g. CdB firmware/hardware version)
    ONLINE,        // Fully initialized and actively answering
    STALE,         // No response within configured threshold
    OFFLINE        // Explicitly disconnected or lost
}
    Components can register standard PropertyChangeListeners to monitor state transitions.

B. Unified Parameter & Configuration Management

  • Bus Comparison: CBUS uses CbusNodeParameterManager and CbusNodeNVManager to abstract parameter reading/writing.
  • Improvement for MCAN: Abstract parameter read/write behind a unified McanParameterManager interface or delegate attached to McanDevice. This provides a consistent parameter access mechanism regardless of whether the device uses CdB indexed parameters or Native CS2 configuration streams.

C. Standard Device Table & UI Components

  • Bus Comparison: CBUS provides CbusNodeTableDataModel and BiDiB provides BiDiBTableModel for node monitoring.
  • Improvement for MCAN: Provide McanDeviceTableDataModel in jmri.jmrix.marklin.swing.devicetable to display all known devices, their system names, family types, firmware versions, CAN classes/modules, and status.

2.3 Criteria 3: Reusability Outside Fully Bootstrapped JMRI

A. Layered Decoupling Architecture

The branch refactor/mcan-library-and-bridge-2 introduced standalone utilities like apps.McanTcpBridge and MarklinCanCodec. To enable third-party Java apps, lightweight gateways, or CLI tools to use the codec and protocol engine without pulling in heavy JMRI GUI/runtime dependencies, the codebase should be organized into two clear layers:

  1. Protocol & Codec Layer (Zero JMRI Runtime Dependencies):
    • MarklinCanCodec (Codec builder & decoder)
    • CdBClassFilter (Class-based pre-filter & classification)
    • CdBMessage (CdB configuration frame factory)
    • McanDeviceIdentity (Native & CdB immutable value objects)
    • CdBReadReply (Read result payload object)
    Dependency rule: This core layer depends only on standard Java SE (and optionally lightweight loggers), making it suitable for standalone distribution or microservices.
  2. JMRI System Integration Layer:
    • McanDeviceManager (Extends AbstractManager<McanDevice>)
    • McanDevice (Extends ProvidedSystemBean / AbstractNamedBean)
    • MarklinTrafficController (JMRI connection memo & listener dispatching)
    • jmri.jmrix.marklin.swing.* (UI panels and tables)

B. Transport Abstraction (Functional Interfaces)

Core protocol handlers and message factories should interact with transport layers through a simple functional interface rather than requiring a full MarklinTrafficController instance: 

@FunctionalInterface
public interface McanFrameSender {
    /**
     * Send a 13-byte raw MCAN frame over the transport.
     * @param frame 13-element integer array representing raw bytes
     */
    void sendFrame(int[] frame);
}

This allows CdBMessage encoders and request/reply correlation engines to operate seamlessly in standalone TCP bridges (like McanTcpBridge), serial daemons, or unit test scaffolds.

3. Revised Implementation Roadmap

Step Component Scope & Responsibilities
Step 1 McanDeviceIdentity Immutable value objects (Native and CdB subclasses). Computes CAN addresses/IDs, system ID fragments (uid-XXXXXXXX / cdb-CC-MM), human-readable strings, and equality semantics. Zero JMRI dependencies.
Step 2 CdBMessage & McanFrameSender Static factories for CdB configuration frames (ping, readParam, writeParam, reset, release, moduleSetup). Uses MarklinCanCodec.builder() and accepts functional McanFrameSender interfaces for pure transport decoupling.
Step 3 McanDevice & McanDeviceState Extends ProvidedSystemBean / AbstractNamedBean. Tracks identity, state enum (DISCOVERED, ONLINE, STALE, etc.), hardware/firmware versions, and timestamps. Fires EDT-safe PropertyChangeEvents on state/metadata updates.
Step 4 McanDeviceManager Implements Manager<McanDevice>, MarklinListener, and CdBConfigListener. Managed by MarklinSystemConnectionMemo. Handles active/passive discovery, bounded timeout task for read correlations, and EDT event dispatching.
Step 5 McanParameterManager Abstraction for reading and writing parameters (CdB indexed params and future CS2 config streams). Handles post-discovery parameter enrichment (firmware/hardware version reads).
Step 6 Swing UI (McanDeviceTableDataModel) Provides visual monitoring and device management in jmri.jmrix.marklin.swing.devicetable aligned with CBUS and BiDiB table models.
